# Decision Log — Materias Canónicas PRD

## Session started: 2026-06-23

### From brainstorming session (pre-PRD)

| # | Decision | Rationale | Status |
|---|---|---|---|
| 1 | Resources belong to subjects, not topics | Topics add too much complexity; plans outdated, many topics not covered | Accepted |
| 2 | Canonical subject as abstract node; subjects are concrete instances | Multiple admin/plan variations of "the same" subject need to share resources | Accepted |
| 3 | Top-down admin mapping (not bottom-up or automatic) | Predictable, controlled; scales to per-university admins later | Accepted |
| 4 | `canonical_display_name` (nullable) field on subjects | Name + plan alone insufficient to determine grouping; admin needs override control | Accepted |
| 5 | Same endpoint for resources, always returns grouped format | Avoids breaking changes; single group returned when no canonical exists | Accepted |
| 6 | No pagination per group | Max ~50-80 resources per group; not needed | Accepted |
| 7 | Upload transparent to student; system propagates to canonical | Student submits to their subject; canonical resolution is backend concern | Accepted |
| 8 | Admin interface in MVP scope | Admin has web admin; needed to manage mappings | Accepted |
| 9 | Resources uploaded before canonical creation are automatically included | Relation is at subject level, not resource level; retroactive by design | Accepted |
